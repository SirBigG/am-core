# Єдиний пошук AgroMega: початковий аудит

- Дата: 2026-10-18.
- Статус: підтверджений локальний аудит; архітектурні пропозиції ще не реалізовані.
- Межі доказів: поточний checkout `am-dev`, код `am-core` і `forum_instance`,
  read-only запити до локального Compose. Production і зовнішній API новин
  не перевірялися. Кількість записів нижче не є статистикою production.

## Що працює зараз

`core/posts/views.py:PostSearchView` обслуговує `/search/`, повертає лише
`Post`, по 20 записів. Запит використовує `SearchRank(text_search,
SearchQuery(q, config="english"))`, відбирає `rank > 0.01` і сортує за рангом.
Немає стабільного додаткового сортування для однакових рангів.

`core/posts/migrations/0019_auto_20190827_1445.py` створює тригер
`tsvector_update_trigger(text_search, 'pg_catalog.english', text)`.
Таким чином індексується лише HTML-текст: назва, категорія, теги та
окремі метадані не входять до вектора. Існуючий GIN-індекс називається
`post_text_se_18be37_gin`. Він є і в локальній БД; усі 3270 статей мають
ненульовий вектор. Це проблема покриття полів і запиту, а не відсутнього індексу.

Для `картопля` локальний `EXPLAIN` поточного запиту показав:

```text
Sort
  Sort Key: ts_rank(text_search, '''картопля'''::tsquery) DESC
  -> Seq Scan on post
       Filter: status AND ts_rank(...) > 0.01
```

Еквівалентний відбір кандидатів через `text_search @@ plainto_tsquery(...)`
використав `Bitmap Index Scan on post_text_se_18be37_gin`.
Це підтвердження доступності індексного шляху, а не порівняння latency:
`EXPLAIN ANALYZE` та навантажувальний тест не запускалися.

Поточний `.active()` перевіряє лише `Post.status`. У Crop Hub вже є
суворіший `core/posts/crop_hub.py:public_posts`: дата публікації не в
майбутньому, канонічний URL заданий, немає неактивних предків категорії.
Політику загального пошуку потрібно визначити явно.

Шаблон уже обіцяє новини, оголошення, компанії й події, яких backend не шукає.
Два наявні тести перевіряють порожній запит та відсутній результат;
позитивного пошуку, ранжування й багатотипової видачі вони не покривають.
`SearchStatistic` зберігає фразу на кожен непорожній запит, включно з
пагінацією, з константою `fingerprint`; розмір поля фрази — 255 символів.

## Джерела та межі видимості

| Ресурс | Власник / поточна поведінка | Що потрібно для пошуку |
| --- | --- | --- |
| Каталожні статті | `posts.Post`, канонічна сторінка статті | Назва з найвищою вагою, текст без HTML, категорія, теги; активність, дата й активні предки категорії |
| Категорії, Crop / Guide Hubs | `classifier.Category`, конфігурації хабів | Один результат на канонічну сторінку категорії; тільки публічні категорії з активним ancestry |
| Оголошення | `adverts.Advert` | Активність і строк `ADVERT_ACTIVE_DAYS`; строк зберігання в sitemap не є строком активної видачі |
| Агромаркет | `companies.Product`, `Post`, `market_offers()` | Переходи на внутрішню market-сторінку сутності; чинні правила активності, категорії, продавця й свіжості; групування продавців |
| Компанії / магазини | `companies.Company` | Тільки активні; назва, опис і публічна географія; поля парсера не індексувати |
| Події | `events.Event` | `status=True`; майбутні й минулі події розрізняти, архів не видавати за майбутнє |
| Щоденники | `diary.Diary` | `public=True`, `is_archived=False`; приватні записи, вкладення й особисті поля не включати |
| Новини | `news.views` → `settings.API_HOST` | У `am-core` немає локальної News-моделі; потрібен контракт експорту / пошуку, оновлення та видалення з боку джерела |
| Публікації та обговорення спільноти | окрема програма `forum_instance` | Власник експортує лише анонімно доступні документи; канонічна публікація без дубля backing topic |
| Державний реєстр | `registry.Variety`, списки та зв'язок `publication` | Не вигадувати окрему detail-сторінку запису; шукати назву / оригінальну назву як атрибути пов'язаної статті, списки — окремі landing pages |

У `forum_instance` пошук Spirit використовує Haystack/Whoosh, а локальний
`PublicForumSearchView` додає публікації через `icontains`. Це окремий
пошук, не підключений до головного `/search/`. Просте копіювання його
queryset не доводить безпечну анонімну видимість усіх станів категорій і тем.

Є відома розбіжність маршрутів: надані workspace-інструкції вимагають
`/forum/`, тоді як forum AGENTS і частина поточного коду описують
`/community/`. Пошук не повинен сам змінювати proxy або маршрути.
Перед підключенням джерела слід узгодити канонічний prefix; власник має
повертати перевірені URL. Ця розбіжність уже описана в ADR 2026-09-06.

## Локальна вибірка

| Сутність | Усього | Поточний публічний / актуальний відбір |
| --- | ---: | ---: |
| Post | 3270 | 3267 через `active()` і через `public_posts()` |
| Advert | 1639 | 0 через `active_objects` |
| Company | 20 | 20 активних; це не перевірка типу магазину |
| Product | 3035 | 0 через `market_offers()` |
| Event | 52 | 52 активних, 0 з `stop >= timezone.now()` |

Локальний PostgreSQL — 15.1. Встановлено лише `plpgsql`, немає `pg_trgm`.
Серед поточних `pg_ts_config` немає української конфігурації.
Нульові актуальні вибірки не є підставою послабити строки видимості.
Потрібні контрольовані fixtures для перевірки оголошень, подій і маркету.

## Пропонований напрям

Єдиний `SearchDocument` у власному Django app `core.search`, незалежний
від моделей контенту. PostgreSQL FTS + GIN для кандидатів; точна назва і
фраза вище збігів у тексті. Окремий нормалізований заголовок із trigram-
індексом для контрольованого пошуку помилок і часткових назв. Це пропозиція
для першої реалізації; вибір слід підтвердити вимірами на реальному обсязі.

`simple` може бути початковою нейтральною конфігурацією для українських
і латинських назв. Вона не дає української морфології. Trigram також не є
морфологією; якість `картопля / картоплі`, апострофів, дефісів і `F1`
потрібно перевіряти окремим набором релевантності. Синоніми й транслітерація
потребують контрольованого словника, без автоматичного об'єднання різних сортів.

Пропонується змішана видача «Усе» з позначеним типом та вкладками за типами.
Маркет — одна картка на каталожну сутність із пропозиціями, а не сотні
однакових карток продавців. Збіг у назві товару також має знаходити відповідну
market-картку; кількість продавців не повинна сама піднімати релевантність.

Для індексу потрібні відтворювана перебудова, інкрементальні оновлення,
видалення/tombstones, контроль відставання й незалежний rollback.
Індекс не має ставати джерелом прав доступу: локальні eligibility-перевірки
застосовуються до count і пагінації. Для віддалених джерел потрібна перевірка
видимості власником з обмеженим timeout і fail-closed поведінкою, поки немає
доведеного протоколу негайного відкликання. Періодичний імпорт і TTL самі
по собі не гарантують відсутності витоку після приховування матеріалу.

Детальні етапи й критерії приймання збережені в локальному плані
`var/agents-work/plans/2026-10-18-unified-search.md`.
